# fiztex-mobile

Приложение для трёх ролей (ученик / родитель / учитель). Expo SDK 57,
React Native 0.86, React Navigation 7. Чистый JS, без TypeScript.

Версии пакетов держит сам Expo — свои ставить нельзя, иначе связка разъезжается:
однажды подняли только пакет `expo` до 57, остальные 25 остались на 54, и сборка
падала на `react-native-svg`, который тянул `buffer` из Node. Проверка — `npx expo
install --check`, починка — `npx expo install --fix`.

```bash
cd mobile && npx expo start        # a — Android, i — iOS, w — web
```

Бэк должен быть поднят (см. корневой `CLAUDE.md`). Базовый URL API вычисляется
в `src/shared/api/config.js`: `EXPO_PUBLIC_API_URL` → LAN-хост Metro →
`10.0.2.2:8080` (эмулятор Android) / `localhost:8080`. На реальном устройстве
через Expo Go ничего настраивать не нужно.

## Что где

| Путь | Что |
|---|---|
| `mobile/` | **реальное приложение** — только здесь пишется код |
| `app/*.jsx`, `Tamos App*.html` | HTML-прототип «Tamos App» — **макет**, источник дизайна |
| `export/` | копия прототипа, не трогать |

Экраны прототипа: `app/screens-student.jsx` (1440 строк), `screens-teacher.jsx`,
`screens-parent.jsx`, `screens-auth.jsx`; дизайн-система прототипа — `app/ds.jsx`.
Это референс вёрстки, а не код для копирования: в RN нет CSS, компоненты берутся
из `mobile/src/shared`.

## Структура приложения

```
mobile/src/
  app/navigation/     RootNavigator, RoleNavigators, CustomTabBar
  features/<роль>/    screens/ — экраны роли (auth, student, parent, teacher,

  shared/ui/          rows.js
  shared/theme/       tokens.js (PHYSTECH, FONT, brand()), ThemeContext (light/dark)
  shared/state/       AppState.js

```

## Правила

**Контракт API.** Эндпоинты искать грепом по `fiztex-back/docs/api-map.md`,
детали — `jq` по `fiztex-back/docs/openapi.json`. В Java-контроллеры за формой
запроса/ответа не ходить. Сгенерированные TS-типы (`fiztex-web/src/lib/api-types.ts`)
здесь не подключены — это JS-проект, но как справочник по полям они точнее мока.

**Запросы.** Новый вызов — метод в соответствующем `src/shared/api/*Api.js`
через `request()` из `client.js`. `fetch` в экранах не писать. Токен приходит
из `features/auth/AuthContext`.

**Дизайн-система.** Экран собирается из `shared/components/ui.js`
(`Card`, `Pill`, `PrimaryButton`, `CircleButton`, `ScreenHeader`, `SectionTitle`,
`Avatar`, `AppHeader`) и `shared/ui/rows.js`. Нет нужного компонента — сначала
завести его в `shared/`, потом собирать экран.

**Цвета и шрифты.** Только из `shared/theme/tokens.js` и `useTheme()`. Хардкод
hex в экранах не заводить. Имена слотов исторические: `green` — оранжевый CTA
`#f5923b`, `blue` — фирменный navy `#274185`.

**Формулы.** Текст вопроса и вариантов ответа может содержать `$…$` — выводить только через
`MathText` из `shared/math`, иначе ученик увидит разметку. Формулы рисует KaTeX внутри
`WebView`; страница с библиотекой и шрифтами лежит в бандле и пересобирается после
обновления katex:

```bash
cd mobile && node scripts/build-katex-asset.mjs
```

Контракт разметки — `fiztex-back/docs/formula-contract.md`.

**Необъявленные имена.** Babel проверяет синтаксис, а не имена: файл с потерянным
импортом компилируется молча и падает уже на экране (так `QuestionBody` переехал в
`shared` без `useTheme`). Перед коммитом:

```bash
cd mobile && node scripts/verify-undefined-names.cjs
```

Без аргументов проходит по всему `src/`. `Buffer` намеренно не в списке известных
глобальных: в Hermes его нет, и обращение к нему — находка, а не шум.

**Мок → API.** `shared/data/mock.js` — временные данные прототипа. Экран
считается готовым, когда данные идут с бэка, а не из мока.

**Текущий урок.** Полоса над нижней панелью навигации у ученика, родителя и учителя
(`shared/components/CurrentLessonBanner` + подключённый `features/lesson/CurrentLessonBar`,
включается флагом `currentLesson` у `CustomTabBar`). В макете это **не пятая вкладка**, и
правильно: вкладка означает раздел, куда приходят и откуда возвращаются, а здесь один шаг
наружу — в карточку конкретного урока. Заодно полоса говорит, какой именно урок откроется,
чего иконка не умеет.

Живёт в панели, а не на «Главной», поэтому доступна с любой вкладки. Хозяйственным ролям
не показывается: уроков у них нет.

Какой урок текущий, решает бэк (`GET /api/lessons/current`) — календарь, подгруппы, замены
и горизонт генерации приложению неизвестны, а недельное расписание ответа не даёт. Своё
здесь ровно одно, и его закрепляет `node scripts/verify-current-lesson.cjs`, — **надпись**:
«Идёт: …» против «Далее: …» берётся из `temporalStatus`, а не сравнением с часами телефона,
и у урока другого дня обязательна дата: «08:30» без неё читается как сегодня.

**Нажатие сначала перезапрашивает урок, потом переходит** (ТЗ §4): иначе после звонка
кнопка ещё минуту вела бы в закончившийся урок. Сорвавшийся перезапрос не блокирует переход
— идём по тому, что уже знаем.

**Пустое состояние не прячет полосу, а занимает её словами** и перестаёт быть кнопкой:
оранжевый со стрелкой обещает переход, которого не будет.

**Место под полосу резервируется всегда** (`BOTTOM_CHROME_HEIGHT`, `useBottomChromePadding`
в `shared/components/Screen`), даже когда её нет: иначе последняя строка списка то пряталась
бы, то нет, в зависимости от того, идёт ли сейчас урок. Экранам-вкладкам полагается брать
отступ оттуда, а не писать «примерно сто» по месту.

**Выбранный ребёнок у родителя — состояние приложения** (`shared/state/SelectedChild`), а
не каждого экрана. Раньше выбор жил на «Главной», в расписании, заданиях и оценках свой, и
они могли показывать разных детей; с этой кнопкой так больше нельзя — она в панели, своего
переключателя не имеет и обязана вести к уроку выбранного ребёнка.

Контракт — `fiztex-back/docs/current-lesson-contract.md`.

**Посещаемость учителя.** Лист урока — экран `attendance` в стеке учителя
(`features/attendance`), вход с плитки на карточке урока. Просмотр и правка — один
экран в двух режимах, как в макете. Вся логика отметки (какие сочетания
`status`/`mark`/`reason` допустимы, что чистится при смене статуса, что уходит в
`PATCH`) живёт в `shared/api/attendanceMap.js`, состояние и команды — в
`useAttendanceEditor`. Экран не вычисляет, можно ли заполнять и публиковать:
`canFill`/`canPublish`/`reminder` приходят с бэка посчитанными. Контракт экрана —
`.cursor/tasks/attendance/screens/AttendanceScreen.md`, проверка логики —
`node scripts/verify-attendance-logic.cjs [ответ /attendance]`.

**Оценки учителя.** Три экрана одного модуля (`features/grades`), и граница между ними
важна: оценки урока (`lesson-grades`, вход с плитки на карточке урока) — единственное
место, где оценку ставят; журнал (вкладка `journal`) — зеркало, которое показывает и
уводит в урок; итоги четверти — вторая вкладка того же экрана, единственное место, где
живёт итоговая. Экран ученика (`journal-student`) второго запроса не делает: лента
строится из уже загруженного ответа журнала.

Права не вычисляются в приложении: лист урока приходит с `canManageGrades`, `writeState`
и `canEdit` у каждой оценки, экран итогов — с `canManage`. Правила окна замещающего,
отменённого урока и «админ оценок не ставит» живут на бэке (`docs/grades-read-contract.md`
§3.1, `docs/final-grades-contract.md` §5). Средние и рекомендации тоже приходят
посчитанными — второй расчёт разошёлся бы с дневником ученика.

Шкала — справочник (`GET /api/grades/scale`), значение оценки в запросах это код (`4+`),
а не число. Итоговая — целое 2…5 без знаков, и удаления у неё нет вовсе (маршрута не
существует), поэтому «Снять оценку» есть только у обычной. Вся раскладка данных и подписи
— `shared/api/gradesMap.js`, проверка логики — `node scripts/verify-grades-logic.cjs
[ответ /grades/sheet]`.

**Материалы урока.** Экран `lesson-materials` (`features/lesson/LessonMaterialsScreen`),
вход — плитка на карточке учителя и строка на карточке ученика; один экран на все три
роли. Подпись берётся из `LessonView.materialCount`, а не из отдельного запроса: счётчик
уже посчитан по правам смотрящего, и у большинства уроков материалов нет вовсе.

**Скрытые материалы отсекает бэкенд**, а не приложение: ученику и родителю они не
приходят ни в списке, ни в счётчике, а на скачивание отвечает отказом. Повторять этот
отбор в `mapLessonMaterial` нельзя — второе место, где живёт видимость, рано или поздно
разойдётся с первым. Поэтому пометка «Только для учителя» рисуется по самому полю
`visibleToStudents`, без вопросов о роли.

Экран только читает: прикладывают материалы, переключают видимость и удаляют их в вебе.
Отсюда и разные пустые состояния — учителю сказано, где это делают.

**Файл открывается внутри приложения, а не через `Linking`**: содержимое отдаётся только
с заголовком `Authorization`, которого системный браузер не пошлёт. Картинку показывает
`Image` с `headers`, остальное — `WebView` с ними же; ссылка (`kind: LINK`) уходит наружу,
ей токен не нужен. Проверка логики — `node scripts/verify-lesson-materials.cjs
[ответ /materials]`, контракт экрана —
`.cursor/tasks/ai-homework/screens/LessonMaterialsMobile.md`.

**Задание-тест у ученика и родителя.** Тест отличается от обычного задания одним полем —
`questionCount > 0`, — и оно приходит и в карточке (`ChildHomeworkView`), и в строке ленты
(`LearnerHomeworkRowView`). В списке помечается словом «Тест»: иначе о нём узнают, только
открыв задание, а в ленте из двадцати это двадцать открытий. Слова про отправку у теста
свои — «Пройден», «Тест пока не пройден»: ребёнок отвечал в приложении, а не присылал файл.

**Оценка за задание — отдельный запрос** `GET /api/grades/my/homework/{id}`
(`useMyHomeworkGrade`). В карточке ДЗ её нет ни в одном ответе, а учительский список по
заданию отдаёт весь класс и родителя туда не пускает. Запрос некритичный: сбой гасится,
карточка остаётся карточкой. **Оценки нет — строки нет:** её отсутствие означает и «не
проверили», и «за это не оценивают», а различить их родителю нечем.

**Ответа ребёнка на родительском экране нет и не будет** — ни текста, ни вложений, ни
версий; бэк их не присылает, и `verify-parent-homework.cjs` держит это со стороны экрана,
подкладывая такие поля нарочно. Обратная связь учителя — единственное содержимое работы,
которое родителю положено.

**Генерация конспекта ИИ.** Шит `HomeworkAiSheet` с карточки задания учителя, только у
черновика (`features/teacher/homework`). Раскладка задачи — `shared/api/homeworkAiMap.js`,
запуск и ожидание — `useHomeworkAiGeneration`, строка «идёт генерация» на карточке —
`useRunningAiJob`.

**С телефона генерируется и текст задания, и вопросы теста.** Тест был закрыт намеренно —
его результат это вопросы с ключом, а редактора вопросов в приложении не было, и
сгенерировать то, чего нельзя прочитать и поправить, значило отдать классу непроверенное.
Редактор появился (`TeacherHomeworkQuestionsScreen`), и причина исчезла: после генерации
шит ведёт прямо в него кнопкой «Проверить вопросы».

Открытых вопросов модель по умолчанию не делает (`openQuestionCount: 0`): их проверка
дороже всего, и добавляет их учитель сам. Текст задания ложится в `description`, который
правит обычная форма.

**Задача переживает экран.** Она живёт строкой в базе: шит закрыли — генерация идёт
дальше, а карточка показывает фазу и обновляет её сама. Отсюда `adopt` — вернувшись, шит
подхватывает уже идущую задачу, а не начинает вторую платную.

Ключ идемпотентности создаётся один раз на открытие шита (`shared/uuid.js` — своя
реализация, `crypto.randomUUID` в Hermes нет). Слова фаз («Читаю материалы урока»,
«Составляю», «Почти готово») дословно совпадают с вебовым `AiJobProgress`: учитель видит
один процесс с двух устройств.

**`awaitingDecision` на телефоне не решается.** Если учитель правил задание после прошлой
генерации, шит говорит об этом прямо и отправляет сравнивать в веб — два конспекта рядом
на экране в 390 точек не помещаются, а выдать это за «готово» значит послать человека
публиковать изменение, которого нет.

Проверка логики — `node scripts/verify-homework-ai.cjs`, контракт —
`.cursor/tasks/ai-homework/screens/HomeworkAiSheetMobile.md`.

**Вопросы теста.** Экран `homework-questions` (`TeacherHomeworkQuestionsScreen`), вход —
карточка задания, и только у теста: у работы с ответом текстом вопросов не бывает вовсе.
Набор сохраняется целиком одним `PUT` — частичного сохранения у вопросов нет ни на сервере,
ни здесь, поэтому «Сохранить» единственный момент, когда что-то уходит наружу.

Вопрос сложён в строку, пока его не открыли: тест из десяти развёрнутых вопросов — экран,
по которому невозможно перемещаться. **Перестановки нет намеренно** — порядок правится в
вебе, а стрелки «выше-ниже» на телефоне промахиваются.

Правила совпадают с `HomeworkQuestionService.validate` на бэке и живут в чистом
`shared/api/homeworkQuestionsMap.js`; проверка — `node scripts/verify-homework-questions.cjs`.
Тип работы (`answerFormat`) выбирается в форме создания и меняется там же, пока у задания
нет вопросов и ответов.

**Прохождение теста — по одному вопросу на экран** (`StudentHomeworkTestScreen`), как во
вступительном тесте. Списком было хуже: длинная лента с вариантами, полями ввода и
фотографиями прокручивается мимо того места, куда только что нажали, а клавиатура
закрывает следующий вопрос. «Окинуть взглядом» возвращает навигатор внизу — номера всех
вопросов, на каждом видно, отвечен он или нет.

Ограничений вступительного теста здесь по-прежнему нет: **ни таймера, ни запрета вернуться,
ни обязательного ответа на каждый вопрос** — те идут от надзора и отведённого времени, а
дома нет ни того ни другого. Черновик в `AsyncStorage` остаётся: приложение уйдёт в фон —
ответы переживут.

Логика, в которой легко ошибиться незаметно (что считается ответом, что уезжает на
сервер), вынесена в чистый `features/homework/homeworkTestModel.js`; проверка —
`node scripts/verify-homework-test.cjs`.

**Античит ДЗ** (`useHomeworkAnticheat`) включает учитель у конкретного задания, флаг
`antiCheatEnabled` приходит с карточкой. Два режима, а не один с флажком:

* `mode: 'test'` — уходы из приложения и возвраты (`APP_BACKGROUND`, `RE_ENTRY`,
  `PAGE_CLOSE`) плюс попытки скриншота;
* `mode: 'content'` (обычное ДЗ) — **только** `SCREENSHOT_ATTEMPT`: переключение
  приложений там нарушением не считается, ученик и должен открыть учебник.

Запрет скриншотов **именной** (`preventScreenCaptureAsync(key)`): карточка задания остаётся
в стеке под экраном теста, и безымянный `allow` при уходе с теста снял бы заодно её защиту.

Предупреждение ученику ничего не прерывает — ни теста, ни ответов, ни оценки: это
сообщение «учитель это увидит». Ошибки записи события до ученика не доходят вовсе.

Учителю журнал показывается блоком `AntiCheatLog` прямо под ответом ученика
(`TeacherSubmissionScreen`) — и ничего не советует: ни «списывал», ни «снизить оценку».
Признак «нарушение или нет» приходит с сервера, а не считается на экране: правило одно на
веб и телефон.

**Фото решения в тесте.** У открытого вопроса учитель может разрешить приложить снимок
(`allowPhoto`, `maxPhotos` приходят в `StudentQuestionView`); блок `AnswerPhotos`
появляется только там, где разрешение есть. Решение задачи по физике — это выкладки и
чертёж, набирать их текстом на телефоне ребёнок не станет.

**Снимок уезжает сразу после выбора, а не вместе с работой.** Тест отправляется одним
запросом, и вложить в него фотографии значило бы отправлять десять мегабайт вместе с
ответами: на школьном Wi-Fi такой запрос срывается и уносит с собой набранный текст.
Отсюда и состояние: у каждой карточки своё, загрузка одной фотографии не блокирует ни
ответ на вопрос, ни соседние вопросы, а отказ не мешает сдать работу без фото.

Лимит повторяется, но не решается на клиенте: считает его сервер по `maxPhotos`. Отбор
«сколько влезет и что сказать про остальные» — чистая `fitPickedPhotos`, проверка —
`node scripts/verify-answer-photos.cjs`. Контракт — `fiztex-back/docs/homework-ai-contract.md`
§9 «Фотография решения к открытому вопросу».

**Оценки ученика и родителя.** Тот же модуль `features/grades`, те же компоненты и тот же
`gradesMap`, что у учителя — расходиться им нельзя: средний балл ученика и средний балл в
журнале учителя обязаны быть одним числом.

* раздел «Оценки» (вкладка `diary` у ученика) — `StudentGradesScreen`, один запрос
  `GET /api/grades/my/subjects`: предметы, их оценки, средние, класс и список четвертей
  приходят вместе. Период необязателен — сервер берёт текущий;
* предмет (`subject`) — `StudentSubjectGradesScreen`: лента из
  `/api/gradebook/students/{id}` плюс итоги из `/api/final-grades/my`, где **нет
  черновиков по построению** — фильтровать статусы на клиенте не нужно;
* чипы оценок на карточках расписания и строка «Оценки» на карточке урока — из
  недельного дневника (`useMyDiaryGrades`), тем же приёмом, что отметки посещаемости:
  отдельный запрос, ошибка гасится, расписание остаётся расписанием;
* годовая до публикации — нейтральный текст «Годовая оценка ещё не опубликована»
  (ТЗ §7 прямо запрещает старое «Появится после завершения всех четвертей»: годовую
  выставляет учитель, и четыре четверти для неё не обязательны).

Родителю предназначены те же экраны — им нужен только `childStudentProfileId`; отдельного
«родительского» раздела заводить не нужно.

**Посещаемость ученика.** Чип на карточке урока (`AttendanceBadge` в `shared/ui/rows.js`)
рисуется из `GET /api/attendance/my-marks?dateFrom&dateTo` — один запрос на неделю,
хук `useMyAttendanceMarks`. Трёхчастную модель бэка (`status` + `mark` + `reason`)
в плоский чип схлопывает `shared/api/attendanceMap.js`, и только он: правило
«опоздание — это посещение, освобождение — не пропуск» живёт в одном месте, иначе
экраны разойдутся с цифрами месячной сводки. Чипа нет, когда отметки нет — включая
неопубликованный черновик учителя и отменённый урок. Контракт —
`fiztex-back/docs/attendance-read-contract.md`.

**Учебник урока у ученика и родителя.** Строка «Учебник» на карточке урока
(`StudentLessonScreen`), шит выбора (`PickerSheet`) и экран просмотра `lesson-textbook`
(`features/lesson/LessonTextbookViewerScreen`) — один на обе роли, родитель передаёт
`childId`. Что делает строка, решает ответ `GET /api/lessons/{id}/textbooks`: учитель выбрал
или назначен один — сразу просмотр со страницы учителя; назначено несколько и ни один не
выбран — сначала шит (ученик выбирает сам, контракт §5); ничего нет — строки нет, как у
материалов. Выбирают учебник и страницы только в вебе.

**Список спрашивается у каждой карточки**, а не по `LessonView.textbookCount`: счётчик
считает только действующее на дату урока и не видит выбор учителя, чьё назначение потом
завершили (`selected.active = false`), — а такой учебник остаётся учебником урока. Запрос
некритичный: сбой гасится, строки просто нет.

**PDF рисует pdf.js внутри WebView** (`shared/pdf/PdfPageViewer`), а не нативный WebView,
как у материалов: макет — это одна страница, «Стр. 24 из 142» и стрелки, а WKWebView листает
PDF только прокруткой и номера страницы не отдаёт, Android же PDF в WebView не рисует вовсе.
Страница с библиотекой и воркером лежит строкой в бандле (~1,4 МБ) и пересобирается после
обновления `pdfjs-dist` (dev-зависимость, legacy-сборка — WebView на Android это системный
Chromium, чью версию приложение не выбирает):

```bash
cd mobile && node scripts/build-pdfjs-asset.mjs
```

`baseUrl` страницы — адрес API, поэтому запросы за файлом идут с того же источника: без CORS.
Файл pdf.js просит кусками (`Range` → `206`), 100-мегабайтный скан ради одной страницы
целиком не качается. Номер на экране — тот, что страница реально нарисовала (`onPage`), а не
последнее нажатие.

**DOCX страниц не имеет** (`pageNavigation = false`): его показывает нативный WebView с
заголовком авторизации, как материалы, — на iOS откроется; Android такие файлы в WebView не
рисует, и экран говорит «откройте его на компьютере», а не показывает пустоту.

**Открывается сразу на странице урока.** Просмотр стартует с начала диапазона учителя
(`startPage` → `lessonRange`), под шапкой — полоса «Задано к уроку: стр. 300–310»: пока ученик
внутри диапазона, это напоминание, ушёл листать — кнопка возврата. Номер страницы внизу —
кнопка «Перейти на страницу» (`TextEditSheet` с цифровой клавиатурой): стрелками до 300-й
страницы не дойти. Следующая страница **внутри диапазона** грузится заранее (`prefetch` в
странице pdf.js, `getOperatorList` подтягивает её куски): замер на 400-страничном учебнике —
ни одна стрелка в 300–310 не ждала сети, а за пределами диапазона лишнего трафика нет.

**Скорость первого открытия зависит от того, как собран PDF, а не от номера страницы.**
pdf.js ищет страницу обходом `/Pages` по порядку и при открытии проверяет последнюю
(`checkLastPage`), загружая каждое описание страницы на пути. Если 400 описаний рассыпаны
по файлу между картинками и перечислены плоским списком, он вытягивает почти весь файл —
даже ради первой страницы. Замеры на одном и том же учебнике в 31 МБ, до показа стр. 300:

| Как собран PDF | Скачано |
|---|---|
| описания рассыпаны, плоский список | 100% |
| описания рассыпаны, дерево по 20 | 12% |
| описания вместе | 2% |
| худший случай, пересохранённый PDFBox (потоки объектов) | 2,6% |

Бэкенд отдаёт ровно запрошенные байты (`206`), а с V83 — **копию, пересохранённую
PDFBox**: у неё худший случай из таблицы и превращается в 2,6%. Приложению ничего делать
не нужно, адрес `/content` тот же; см. «Учебники» в `fiztex-back/CLAUDE.md`.

Раскладка — чистый `shared/api/textbookMap.js`, проверка —
`node scripts/verify-lesson-textbooks.cjs [ответ /textbooks]`. Сама страница pdf.js
проверялась в Chromium через dev-сервер веба (он проксирует `/api`, то есть тот же источник);
в симуляторе и на устройстве — нет (см. корневые заметки о симуляторе). Карточка урока
учителя в мобилке строки «Учебник» пока не имеет — макета на неё нет.

**Техника и инвентарь.** Раздел Super Admin (`features/equipment`): три вкладки —
«В наличии», «Выдано», «История», — карточка экземпляра, выдача пачкой, возврат, передача,
проблемы и списание. Модуль повторяет ключи (`features/keys`), и это осознанно: ТЗ прямо
просит переадаптировать их дашборд, а не рисовать второй.

**`SUPER_ADMIN` впервые пускают в приложение** (`MOBILE_ROLES`), и состоит оно у этой роли
ровно из одного раздела: остальное он делает в панели. Навигатор свой (`SuperAdminApp`) —
делить с `StaffApp` нечего, у Super Admin нет вкладки заявок.

**Правила не вычисляются в приложении.** Что можно сделать с экземпляром, раскладывает
`unitActions` из готовых `issuable` и `transferable`: у техники выдачу и передачу запрещает
только «Потеряна», а «Повреждена» и «Не работает» — нет (отдельного процесса ремонта в MVP
нет, неисправное выдают техслужбе). Списание выданного подтверждается именем держателя, и
если вещь выдали в другой сессии, сервер отвечает отказом с новым держателем — диалог
переспрашивает, а не закрывает чужую выдачу молча.

**Занятое название позиции — развилка, а не ошибка ввода:** сервер отвечает 409 с самой
позицией, и форма переключается на «добавить экземпляры в неё». Позиция, у которой всё
списано, живёт в справочнике `GET /api/equipment/items` — в рабочих списках её нет.

**«Моя техника» (`MyEquipmentCard`) — read-only блок получателя**, и он есть у каждой роли,
которой техника может достаться: учитель — на главной, администратор, службы, охрана и
психолог — в «Я», Super Admin — над списком «В наличии». **Рядом с ним везде стоит `MyKeysCard`**:
раздел ключей принадлежит охране, и без этого блока сотрудник, за которым числится ключ, не
видел его в приложении нигде — блок ставили только на главную учителя. Кнопок в блоке нет: вернуть, передать
и списать сотрудник не может, а кнопка, которая ничего не делает, хуже её отсутствия. Нет
активных выдач — блока нет вовсе.

Раскладка и слова — чистый `features/equipment/equipmentModel.js`, проверка —
`node scripts/verify-equipment-logic.cjs`. Контракт — `fiztex-back/docs/equipment-contract.md`.

**Кабинет психолога и профиль охраны.** Роль психолога перестала быть заглушкой: весь цикл
опроса живёт в телефоне (`features/psychologist`) — список, карточка, редактор вопросов,
выбор классов, публикация, завершение, сводка и именные ответы. Вкладок две: «Опросы» и
«Я». У охраны к трём вкладкам ключей добавилась та же «Я»: заявки она заводит по правам с
самого начала, но экраны висели зарегистрированными без единого входа, а выход прятался в
меню аватара.

**Профиль один на пять ролей** (`StaffProfileScreen`): администратор, уборка, техслужба,
охрана, психолог. Содержимое у них совпадает полностью — сервисные заявки, свои ключи и
техника, тёмная тема, Face ID, выход; различает их подпись под именем, и её даёт роль.

**Психолог заводит сервисные заявки** — его единственное разрешение на бэке
(`SERVICE_REQUEST_CREATE`, добавлено вместе с этими экранами). Исполнителем он не
становится: очередь и «создать и взять в работу» открывает не разрешение, а обслуживаемая
очередь, которой у роли нет.

**Опрос не оценивается**, и редактор это отражает: у варианта только текст, правильных
ответов, баллов и перемешивания нет вовсе. Набор вопросов сохраняется целиком одним `PUT` —
частичного сохранения нет ни на сервере, ни здесь. Правку идущего опроса закрывает сервер
(`canEdit`), и экран показывает вопросы только для чтения, а не прячет кнопку молча.

**Аудитория — только ученики.** Классы приходят своим эндпоинтом
(`/admin/surveys/audience-classes`): общий справочник психологу закрыт. Родителей сервер
отклоняет, поэтому переключателя для них нет — выбор, у которого одно положение, не выбор.
Число учеников в классе показано потому, что получатели фиксируются снимком при публикации.

**Именные ответы** есть только у именного опроса и только у отправивших: черновик ученика
сервер не отдаёт. У анонимного экран обещает одну сводку и так и говорит.

Раскладка и слова — чистый `shared/api/surveyAdminMap.js`, проверка —
`node scripts/verify-survey-admin.cjs`.
